## Rules of this milestone

- **Machine (D-052, the owner is away):** up to 4 subagents, cargo jobs and test threads at their defaults,
  `nice` optional. The disk rules stay (`df -h /` before a heavy build, `target/` under about 20 GB: delete
  `target/debug/incremental` only when no `cargo`/`rustc` runs).
- **Four agents share one working tree and one `target/`.** Stay in the files your part lists. The files
  everyone touches (`actions.rs`, `workspace.rs`, `settings.rs`, `settings_view.rs`, `ui_tests.rs`,
  `kerno-core/src/lib.rs`, `storage.rs`, `Cargo.toml`) get small, local edits only: add your lines, never
  reformat or reorder what is there, never revert a change you did not make. New UI tests go in a new file
  `crates/kerno/src/ui_tests/<part>.rs` (one `mod` line in `ui_tests.rs`). A build that fails in a file that
  is not yours is another agent in the middle of an edit: wait a minute and build again; if it still fails
  after ten minutes, say so in your report, do not fix their file. Run `cargo fmt` on your own files only
  (`rustfmt --edition 2024 <files>`), not `cargo fmt --all`. Leave the tree compiling whenever you stop.
- **Never** touch the `kerno-site` branch or worktree, another agent works there. It may drive the Kerno
  app: before launching the app (captures, bench) check `pgrep -x kerno` and wait while one runs. Parts do
  not launch the app unless they say so.
- **Containers:** the four `kerno-*` containers are up for the whole milestone (main session). Only Part 1
  adds one (`kerno-ssh-jump`) and Part 5 its own bench containers; nobody stops, restarts or disconnects
  the shared ones (other agents are testing against them).
- **No process-wide state in tests.** The edition is 2024: `std::env::set_var` is `unsafe`, and `unsafe` is
  denied. Code that reads `HOME`, `PATH`, `PGPASSFILE` or a config file takes them as parameters (a small
  `struct` with the real values built once in the app), so tests pass a temporary directory.
- **Secrets:** nothing new on disk, in logs, in arguments of a child process, or in an environment variable
  of a child process. A secret reaches a child through a pipe.
- **Network:** nothing leaves the machine except the database connection, the update check (§1) and, when
  the user turned it on and asks, the AI endpoint they configured (J17). Tests never reach a real remote
  host: fakes on `127.0.0.1` only.
- **Each J item ends with:** unit and integration tests on PostgreSQL 17, MySQL 8.4 and MariaDB 11 where it
  applies (`KERNO_REQUIRE_CONTAINERS=1`, not skipped), UI tests for every new surface, a palette or
  context-menu entry where it fits §3, its row in `docs/FEATURES.md` (new section "J. v1.1", the columns of
  the other sections, issue numbers in the item text), the lines of `docs/ROADMAP.md` and
  `docs/DECISIONS.md` it contradicts corrected, a "Done:" note under its part here. Captures (light and
  dark, `docs/screenshots/final/`) are taken in Part 16 by the main session's capture agents: say in your
  report which screens to capture and how to reach them.
- **Report** as in `docs/plans/README.md`: files, signatures, the exact test commands with their
  `test result:` lines, what is not done or not verified. Do not commit.
- Quote the issue numbers of `docs/COMPETITOR-ISSUES.md` in test names or their doc comments.

## Part 1 — J2: SSH through the system OpenSSH

Demand: DBeaver #5845, #14749, #4516, #17976; Beekeeper #1240, #1344, #940.

**Model** (`config.rs`): `SshConfig` gains `client: SshClient { Builtin, OpenSsh }` (serde default
`Builtin`, so stored connections do not change) and `jump: Option<String>` (`user@host:port`, several
separated by commas, as `ssh -J`). With `OpenSsh`, `host` may be an alias of `~/.ssh/config`, and `port`,
`user` and the key are optional (the config provides them). Password authentication exists only with
`Builtin`; `validate()` says so in plain words. New connections default to `OpenSsh` when `ssh` is found
and the authentication is not a password.

**Tunnel** (`openssh.rs`, used by `connector.rs` beside the russh `Tunnel`, same two operations the
drivers use today — look at how `Connector` hands a tunnel to each driver and keep that surface; an enum
of the two tunnels, not a trait):

- `ssh -N -L 127.0.0.1:<port>:<db host>:<db port> -o ExitOnForwardFailure=yes -o BatchMode=yes
  -o ServerAliveInterval=<keep-alive> -o ServerAliveCountMax=3 [-F <config>] [-J <jump>] [-p <port>]
  [-l <user>] [-i <key> -o IdentitiesOnly=yes] -- <host>`, arguments as a list, no shell,
  `kill_on_drop(true)`, stdin null, stderr piped. The local port: bind `127.0.0.1:0`, read the port, drop
  the listener, start `ssh`, then poll a connect until it answers or `ssh` exits or the connect timeout
  passes (retry once on "Address already in use"). `-W` through the child's stdin/stdout is the
  alternative if it fits the drivers better: decide after reading `connector.rs`, write it in D-054.
- `ssh` is found on `PATH` and in `/usr/bin`, `/opt/homebrew/bin`, `/usr/local/bin` (a GUI app's `PATH` is
  short); when missing, the dialog says "OpenSSH was not found on this computer; use the built-in client."
- **Key passphrase** ("enter it here"): never in an argument or the environment. `SSH_ASKPASS` points at
  the running executable with `SSH_ASKPASS_REQUIRE=force` and `KERNO_ASKPASS=<path of a one-shot Unix
  socket in a 0700 temporary directory>`; `kerno-core::openssh::answer_askpass()` (called first thing in
  `main`, returns `Some(exit code)` when the variable is set) connects, reads the answer and prints it; the
  parent answers once with the passphrase from the secret store and closes the socket. For core
  integration tests add a `[[bin]]` (or `[[test]]` helper) so `CARGO_BIN_EXE_…` gives an executable that
  calls the same function; the app uses `current_exe()`. Without a stored passphrase `BatchMode=yes`
  makes `ssh` fail fast and the error is explained.
- **Host keys** are OpenSSH's (`known_hosts`). "Host key verification failed" is explained ("The server
  `x` is not in ~/.ssh/known_hosts yet…") with a "Trust this host and retry" action that reruns with
  `-o StrictHostKeyChecking=accept-new` (a changed key still fails: say that it changed and never offer to
  accept it).
- `-F`: `ssh` ignores `$HOME`, so tests cannot redirect it. The config file is a parameter
  (`OpenSshEnv { ssh: PathBuf, config: Option<PathBuf>, askpass: PathBuf }`); the app builds it once, with
  `KERNO_SSH_CONFIG` as an optional override (documented in the README beside the other variables).
- Closed tunnel: the child exited (`try_wait`); `Connector::tunnel_closed` covers both tunnels, so
  auto-reconnect keeps working.

**`~/.ssh/config` aliases** (`openssh.rs`, pure, unit-tested): `host_aliases(config: &Path) -> Vec<String>`
reads the file and its `Include`s (relative to the file's directory, `~` expanded, globs through
`std::fs::read_dir` + a `*`/`?` match; depth capped at 8), keeps `Host` names without `*`, `?` or `!`,
in order, without duplicates; `Match` blocks are skipped. The dialog's SSH host field is a free-text
field with these in a dropdown (same pattern as the database dropdown, `conn-database-list`).

**Errors** (`error.rs`, `explain`): `ssh`'s stderr is mapped to plain words with the next step — permission
denied (publickey), passphrase needed ("The key in ~/.ssh/id_rsa needs a passphrase: load it with ssh-add
or enter it here"), host not resolved, connection refused / timed out, host key unknown / changed, bad
permissions on the key or config, jump host failures (name which hop), forward refused
(`administratively prohibited`). The raw stderr stays below, as for database errors.

**Dialog** (SSH tab): Client (OpenSSH / Built-in), Host (alias dropdown), Port, User, Jump host, Key file,
Passphrase, keep-alive; fields that do not apply are hidden, not greyed. Test connection works unchanged.

**Fixtures:** `kerno-ssh-jump` in `docker-compose.yml` (same image as `kerno-ssh`, host port 52223, on
the compose network so it reaches `kerno-ssh:22`); `scripts/test-env.sh` generates an RSA 3072 key pair
beside the existing test key and both public keys go to `authorized_keys` of both containers; add the
jump container to `test-env.sh up/down` and to `kerno_core::testing`. You may `docker compose up -d
--build ssh ssh-jump` (only those two services; tell the main session if `kerno-ssh` had to be recreated).

**Tests:** unit (argument list for every combination — no secret in it; alias parsing with `Include`,
globs, wildcards, `Match`; stderr explanations). Integration `crates/kerno-core/tests/openssh.rs` with a
temporary config (`UserKnownHostsFile`, `IdentityFile`, aliases): tunnel to PostgreSQL and MySQL through
`kerno-ssh` with the ed25519 key; **with the RSA key file** (GOAL-2 criterion 2); with a
passphrase-protected key through askpass; **through the jump host** both with `-J` (Jump host field) and
with `ProxyJump` in the config under an alias; unknown host key → explained, then accepted with
"trust"; wrong key → explained; the child is gone after drop. Driver tests: connect through the OpenSSH
tunnel on the three engines. UI tests (`ui_tests/openssh.rs`): the dialog lists the aliases of a
temporary config; a connection saved with an alias and a jump host connects and runs a query; the
built-in client still connects with a password.

Docs: D-013 says RSA key files are refused: they now work through OpenSSH (the built-in client still
refuses them, with a message pointing to OpenSSH). README "SSH" paragraph. No `rsa` crate comes back.

Done: `kerno-core/src/openssh.rs` (detection, arguments, the `ssh -N` forwarding a private Unix socket,
askpass, `Host` aliases), `Tunnel` / `TunnelStream` as enums of the two clients, `connector::open_tunnel` (also
used by the tools' dialog), `SshClient` and `jump` in `SshConfig`, plain words for ssh's messages in
`error::explain`, the dialog's Client / alias list / Jump host, `kerno-ssh-jump` (52223). Host keys are trusted
by fingerprint through ssh's own question rather than `accept-new` (D-056). Tests listed in `docs/FEATURES.md`
(J2); `cargo tree -i rsa` stays empty.

## Part 5 — J8 and J9

**J8 reorder columns** (Beekeeper #1341). `table_draft.rs`: the draft's column order becomes meaningful
for an existing table; on MySQL and MariaDB a moved column produces `ALTER TABLE t MODIFY COLUMN <the
column's full definition> FIRST | AFTER <previous>` (definition from the same code as "modify column", so
type, nullability, default, `AUTO_INCREMENT`, generated expression, charset/collation and comment are
kept), minimal number of moves (longest increasing subsequence stays put), combined with other pending
changes in the right order. Structure editor: "Move up" / "Move down" buttons and menu entries on a
column row (drag if the kit's list makes it straightforward), live DDL preview. On PostgreSQL the
controls are disabled with the reason: "PostgreSQL cannot move a column: its position is fixed when the
column is created. Recreate the table, or use a view, to change the order." Tests: unit (SQL, minimal
moves), integration on MySQL and MariaDB (order changed, definitions identical before/after via
`table_structure`, with a generated column and an auto-increment key), UI (`ui_tests/reorder.rs`).

**J9 benchmarks** (Beekeeper #752, #135, #702, #2325; DBeaver #6903). New bench modes in `bench.rs` and
steps in `scripts/bench.sh` (each step can run alone: `scripts/bench.sh --only wide|navigator|import|
reconnect`); scratch objects are `kerno_bench_*`, created by the script and dropped by it, pass or fail.

1. **300 columns** (`wide`): `kerno_bench_wide` in `kerno-postgres` (300 mixed columns × 20,000 rows) and
   the same in `kerno-mysql`; the `scroll` mode on it, vertical and horizontal; target average frame
   < 16 ms.
2. **200 schemas, 1,200 tables** (`navigator`): a scratch database `kerno_bench_many` on `kerno-postgres`
   with 200 schemas, one of them holding 1,200 tables (5 columns each); on MySQL a database with 1,200
   tables. New mode `KERNO_BENCH=navigator`: connect, expand the database: time from the click to the
   frame that shows the schemas (target < 300 ms); expand the 1,200-table schema's Tables: time to the
   frame that shows them (target < 500 ms). If a target is missed, fix the navigator (one catalog query
   per level, virtual rows), do not move the target.
3. **200 MB `.sql` import** (`import`): the script generates a 200 MB file of `INSERT`s for a scratch
   database; the Execute script tool runs it. It must show progress (bytes of the file sent / total:
   feed the client through its stdin from the file if `-f` gives no progress), keep drawing frames (the
   mode records frame intervals during the import: average and maximum) and cancel within 2 s (measured
   in a second run, cancelled at 30 %). Report the total time and the throughput. Add the progress to
   the wizard if it is missing (unit + UI test).
4. **Reconnect** (`reconnect`): a **dedicated** container `kerno-bench-pg` (postgres:17, its own network
   `kerno-bench-net`, host port 55440), never the shared ones. The app is connected with a query tab;
   the script runs `docker network disconnect`, waits 10 s, `docker network connect`, and notes the time
   the network is back; the mode reports when a `SELECT 1` succeeds again; target < 5 s after the
   network is back. If Docker does not restore the published port on reconnect, use `docker pause` /
   `unpause` or an `iptables`-free equivalent on that container and say so in the method. Fix the
   auto-reconnect if the target is missed (detection through keep-alive, retry with back-off starting

- **Core** (`vim.rs`, pure, no GPUI): `Vim { mode: Normal | Insert | Visual | VisualLine, pending
  (count, operator, register text, last change for `.`, last `f`/`t`, search) }`,
  `fn key(&mut self, key: Key, buffer: &Buffer) -> Vec<Effect>` where `Buffer` is the text + cursor (+
  selection) and `Effect` is `Move(offset) | Select(range) | Replace { range, text } | Undo | Redo |
  Yank(text) | SetMode | Save | CloseTab | Search(…) | Bell`. Motions `h j k l w b e 0 ^ $ gg G f t %`
  (with counts; `%` uses `matching_bracket`); operators `d c y` with motions and text of visual
  selections, `dd yy cc`, `x`, `p P` (linewise and characterwise registers; the system clipboard is the
  unnamed register), `u`, `⌃r`, `.`; `i a I A o O` to insert, `v V`, `Esc`; `/pattern` + `n N`; `:w`
  saves the file, `:q` closes the tab (`:wq`, `:q!` too). **One unit test per motion and per operator**,
  plus counts, `.` repeat, and Unicode (multi-byte) text.
- **App** (`query/vim.rs`): with Settings → Editor → "Vim mode" on, the query editor's keys go to `Vim`
  first in Normal and Visual (a capture-phase key handler on the editor's wrapper) and the effects are
  applied through the kit's `InputState` API (cursor, selection, replace as one undoable edit, the
  kit's undo/redo); Insert mode passes everything to the editor except `Esc`. Arrows, Home/End, Page
  keys, the mouse and every ⌘ shortcut (run, save, palette, completion keys) work in every mode. The
  mode shows in the status bar (`NORMAL` / `INSERT` / `VISUAL`), the cursor is a block in Normal; `:`
  and `/` open a one-line command field at the bottom of the editor. With the setting **off nothing is
  installed**: no handler, no status item (test: the same key sequence types text).
- UI tests (`ui_tests/vim.rs`): off → `dd` types "dd"; on → `ddp`, `ciw` + text + `Esc`, `3j`, `/` + `n`,
  `:w` saves the file, `:q` closes the tab, arrows move in Normal and Insert, ⌘↵ still runs.
