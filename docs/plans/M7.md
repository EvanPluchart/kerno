## Part 1 — Table DDL from a draft (core + dialects) — `opus`

New file `crates/kerno-core/src/table_draft.rs` (declared in `lib.rs`), dialect methods in
`crates/kerno-core/src/dialect.rs`, overrides in `crates/kerno-postgres/src/dialect.rs` and
`crates/kerno-mysql/src/dialect.rs`, integration tests `crates/kerno-postgres/tests/alter.rs` and
`crates/kerno-mysql/tests/alter.rs` (pattern: `tests/generate.rs` of each driver, with its `cleaning_up`).
Test-first.

```rust
/// A table as the form editor holds it. `original` names tie a draft item to what exists.
pub struct TableDraft {
    pub table: TableRef,                 // schema + name (the new name when renamed)
    pub comment: Option<String>,
    pub columns: Vec<ColumnDraft>,       // in display order
    pub indexes: Vec<IndexDraft>,
    pub foreign_keys: Vec<ForeignKeyDraft>,
    pub primary_key: Vec<String>,        // column names, in key order
}
pub struct ColumnDraft {
    pub original: Option<String>,        // name in the existing table; None for a new column
    pub name: String,
    pub data_type: String,               // as typed: "numeric(10,2)", "varchar(190)", "bigint unsigned"
    pub nullable: bool,
    pub default: Option<String>,         // SQL expression, as typed
    pub comment: Option<String>,
    pub auto_increment: bool,            // PG: GENERATED BY DEFAULT AS IDENTITY; MySQL: AUTO_INCREMENT
}
pub struct IndexDraft { pub original: Option<String>, pub name: String, pub columns: Vec<String>, pub unique: bool }
pub struct ForeignKeyDraft {
    pub original: Option<String>, pub name: String, pub columns: Vec<String>,
    pub referenced_table: TableRef, pub referenced_columns: Vec<String>,
    pub on_update: String, pub on_delete: String,      // "NO ACTION", "CASCADE", "SET NULL", "RESTRICT", "SET DEFAULT"
}
impl TableDraft {
    pub fn new(table: TableRef) -> Self;                         // one `id` auto-increment primary key column
    pub fn from_structure(table: &TableRef, structure: &TableStructure) -> Self;   // originals filled
    pub fn validate(&self) -> Vec<String>;                       // empty names, duplicates, PK/index/FK on a
                                                                 // missing column, FK column count mismatch,
                                                                 // no column at all
}
/// What changed, in the order statements must run.
pub enum TableChange {
    RenameTable { to: String },
    SetTableComment(Option<String>),
    DropForeignKey(String), DropIndex(String), DropPrimaryKey,
    DropColumn(String),
    RenameColumn { from: String, to: String },
    AddColumn(ColumnDraft),
    AlterColumn { name: String, from: ColumnInfo, to: ColumnDraft },   // type, nullability, default, comment
    AddPrimaryKey(Vec<String>),
    AddIndex(IndexDraft), AddForeignKey(ForeignKeyDraft),
}
pub fn changes(original: &TableRef, structure: &TableStructure, draft: &TableDraft) -> Vec<TableChange>;
```

`changes` is pure: drops of keys and indexes first, then columns (drop, rename, add, alter), then primary
key, indexes and foreign keys, table rename last (a renamed index or foreign key is drop + add; an index
whose columns or uniqueness changed too). Indexes that back a primary key or a unique constraint are not
listed as indexes in the draft (`IndexInfo` tells: read its fields; if it does not tell, add the flag in the
drivers' `introspect.rs`). A draft equal to the structure gives no change.

Dialect (default implementations are standard SQL; overrides where the engine differs):

```rust
fn create_table_sql(&self, draft: &TableDraft) -> Result<Vec<String>>;   // CREATE TABLE, then indexes, comments
fn alter_table_sql(&self, table: &TableRef, changes: &[TableChange]) -> Result<Vec<String>>;
```

- PostgreSQL: one `ALTER TABLE … <action>` statement per change; `ALTER COLUMN c TYPE t`,
  `SET/DROP NOT NULL`, `SET DEFAULT e` / `DROP DEFAULT` (only the differing parts are emitted);
  `RENAME COLUMN a TO b`; `ADD CONSTRAINT n FOREIGN KEY (…) REFERENCES s.t (…) ON UPDATE … ON DELETE …`;
  `DROP CONSTRAINT n`; primary key `ADD PRIMARY KEY (…)` / `DROP CONSTRAINT <pk name>` (name from the
  structure's constraints); `CREATE [UNIQUE] INDEX n ON s.t (…)`, `DROP INDEX s.n`; comments
  `COMMENT ON TABLE / COLUMN … IS '…'` (NULL to remove); auto-increment `GENERATED BY DEFAULT AS IDENTITY`
  (`ADD GENERATED …` / `DROP IDENTITY` when toggled); `RENAME TO`.
- MySQL / MariaDB: `MODIFY COLUMN name type [NOT NULL] [DEFAULT e] [AUTO_INCREMENT] [COMMENT '…']`
  (always the full definition), `RENAME COLUMN a TO b`, `ADD COLUMN …`, `DROP COLUMN`, `ADD [UNIQUE] INDEX n
  (…)`, `DROP INDEX n`, `ADD CONSTRAINT n FOREIGN KEY …`, `DROP FOREIGN KEY n`, `DROP PRIMARY KEY`,
  `ADD PRIMARY KEY (…)`, `COMMENT = '…'`, `RENAME TO db.name`. Column and table comments are inline in
  `CREATE TABLE`.
- Identifiers through `quote_ident`, strings through `quote_string`, types and default expressions as
  typed (they are SQL the user wrote; they are shown in the preview before anything runs).

Tests: unit tests of `changes` (each kind of change, order, no change), of `validate`, of both dialects'
statements (exact strings); integration tests that run on the servers: create a table from a draft, read
its structure back, `from_structure` then edit (add, rename, retype, drop a column; toggle nullability;
change a default; add and drop an index and a foreign key; change the primary key; comments; rename the
table), apply the statements, read the structure again and compare with the draft. PostgreSQL, MySQL and
MariaDB.

**Part 1 is done** (commit after `343ac94`: `table_draft.rs`, `Dialect::create_table_sql` /
`alter_table_sql`, `IndexInfo::backs_constraint`, `tests/alter.rs` in both drivers). What it changed for the
next parts: `TableChange::DropPrimaryKey(String)` carries the constraint name; MySQL / MariaDB send at most
two statements (foreign-key drops, then one combined `ALTER TABLE`, which InnoDB applies all or nothing), so
the Part 3 warning about partial application only concerns that first statement; `validate` also refuses a
nullable primary-key or auto-increment column; `from_structure` leaves out indexes a draft cannot describe
(partial, expression, non-btree, MySQL's implicit foreign-key indexes); column order cannot be edited.

**Part 1b — must be fixed before Part 3 ships (`opus`, small, core + MySQL driver):** `MODIFY` / `CHANGE`
rewrite the whole column definition and `ColumnInfo` does not carry `ON UPDATE CURRENT_TIMESTAMP` (nor
`INVISIBLE`), so editing such a column from the form silently loses it (fixture: `kerno.customers.updated_at`).
Add `ColumnInfo::on_update: Option<String>` read from `information_schema.columns.EXTRA` (MySQL:
`DEFAULT_GENERATED on update CURRENT_TIMESTAMP`; MariaDB: `on update current_timestamp()`), carry it in
`ColumnDraft` (kept as is by the form, shown read-only), write it back in the MySQL column definition, and
test on both servers that a comment-only edit of that column keeps the auto-update (update a row, the
timestamp moves). PostgreSQL leaves the field `None`.

## Part 3 — Create and alter tables through a form (app) — `opus`, after Parts 1 and 2

Files: new `crates/kerno/src/structure/editor.rs`; `structure/tab.rs` ("Edit table…"), `navigator/view.rs`
(`Action::CreateTable` opens the form instead of a template), `workspace.rs`, `ui_tests.rs`.

A dialog or a tab (a tab is better: the form is wide) `TableEditor` holding a `TableDraft`:

- Name, schema (fixed), comment.
- Columns as rows of inputs: name, type (free text input with a dropdown of common types per engine:
  PostgreSQL `integer, bigint, numeric(10,2), text, varchar(255), boolean, date, timestamptz, uuid, jsonb`;
  MySQL `int, bigint, decimal(10,2), varchar(255), text, tinyint(1), date, datetime, json`), nullable
  checkbox, default, primary-key checkbox, auto-increment checkbox, comment; buttons Add column, remove,
  move up / down.
- Indexes: name, columns (multi-select from the draft's columns), unique; add / remove.
- Foreign keys: name, columns, referenced table (free text `schema.table` with completion from
  `session.objects`), referenced columns, on update / on delete dropdowns; add / remove.
- A live **DDL preview** pane (read-only, monospace) recomputed on every change from
  `dialect.create_table_sql(&draft)` (new table) or `dialect.alter_table_sql(&table, &changes(...))`;
  validation messages (`draft.validate()`) shown above it in the danger colour; "No change" when empty.
- "Apply" goes through `sql_confirm::open` with the statements joined (destructive when a column, index or
  key is dropped; production asks twice; a read-only connection has no Apply and says why). The statements
  run one after the other on the tab's session; PostgreSQL in one transaction (`START TRANSACTION` …
  `COMMIT`, rollback on error), MySQL / MariaDB without (DDL commits implicitly: say so in the confirmation
  text: "MySQL applies each statement at once; a failure leaves the earlier ones applied."). On success:
  notification, the navigator node is refreshed (`Navigator::refresh` of the schema's Tables folder: look at
  how `confirm` / `execute` refresh after a drop), the structure tab reloads; on failure the error with the
  failing statement, the form stays.

Tests: `a_table_is_created_from_the_form` (three engines: fill the form through its inputs and buttons,
preview shows `CREATE TABLE`, apply, the table exists with those columns),
`a_table_is_altered_from_the_form_with_a_preview` (add, rename, retype, drop a column, add an index; the

## Part 4 — Sources, extensions and enums (drivers + app) — `opus`

1. **View, function and procedure source** (F3). `Dialect::replace_source_sql(&self, object: &ObjectRef, ddl:
   &str) -> Result<String>`: the script that replaces the object by an edited definition. PostgreSQL: views
   `CREATE OR REPLACE VIEW` (the DDL from `pg_get_viewdef` wrapped accordingly; materialized views cannot be
   replaced: `DROP MATERIALIZED VIEW` + `CREATE`, flagged destructive), functions and procedures already
   come as `CREATE OR REPLACE` from `pg_get_functiondef`. MariaDB: `CREATE OR REPLACE VIEW / PROCEDURE /
   FUNCTION`. MySQL: views `CREATE OR REPLACE VIEW`; routines `DROP PROCEDURE IF EXISTS x;` then `CREATE`
   (sent as two statements, not with `DELIMITER`: the app sends each statement on its own, so a routine
   body goes as one statement — check how `split_statements` and the MySQL session handle `BEGIN … END`
   bodies and use a `DELIMITER //` script if that is what the splitter needs).
   App: navigator action `Action::EditSource` "Edit source" on views, materialized views, functions and
   procedures: opens a query tab titled with the object, holding that script, in **source mode**
   (`QueryTab` flag): the toolbar shows "Apply source" which runs the whole script after
   `sql_confirm::open` (preview of the script; destructive when it contains a `DROP`); the usual Run stays
   available. After a successful apply the navigator node is refreshed. Tests on three engines: edit a
   view's `SELECT`, apply, the view returns the new column; edit a function body, apply, calling it returns
   the new value; cancel applies nothing; read-only connection refuses.
2. **PostgreSQL extensions** (F4). Catalog: installed come from `Session::extensions()`; available from
   `SELECT name, default_version, comment FROM pg_catalog.pg_available_extensions WHERE installed_version IS
   NULL ORDER BY name` (add `Session::available_extensions()` with a default `Ok(vec![])`, implemented in
   the PostgreSQL driver). Dialect: `create_extension_sql(name) -> "CREATE EXTENSION IF NOT EXISTS \"name\""`,
   drop already goes through `drop_sql` (check `ObjectRef` has an extension variant; add it if not, with
   `DROP EXTENSION`). App: on the "Extensions" node, "Install extension…" opens a searchable list of the
   available ones (name, version, comment), choosing one opens `sql_confirm`; on an extension, "Drop…".
   Test: install `citext` or `pg_trgm` in the scratch database if not installed (check what the fixture
   already installs; use one it does not), see it in the tree, drop it. The container's image ships the
   contrib extensions.
3. **Enums** (F4). PostgreSQL: on the "Types" folder "Create enum…" (name, labels one per line →
   `CREATE TYPE s.n AS ENUM ('a', 'b')`); on an enum type "Add value…" (`ALTER TYPE s.n ADD VALUE 'x'
   [BEFORE|AFTER 'y']`), "Rename value…" (`ALTER TYPE s.n RENAME VALUE 'a' TO 'b'`), Drop exists. Dialect
   methods `create_enum_sql`, `add_enum_value_sql`, `rename_enum_value_sql` (PostgreSQL only; `Unsupported`
   by default, and the menu entries are absent on MySQL, where enums are column types edited in the table
   form). All through `sql_confirm` with a small form for the inputs (see `Statement::Named` in
   `sql_confirm.rs`; extend it or write a two-field variant). Tests: create, add, rename, drop on
   PostgreSQL; the tree shows the labels.
