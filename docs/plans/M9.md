# Milestone 9 — Performance pass and `docs/BENCH.md` (spec §5, GOAL criterion 5)

Read `docs/plans/README.md` first. Targets (release build, Apple Silicon):

| What | Target |
| ---- | ------ |
| Cold start to first interactive frame | ≤ 400 ms |
| Idle RSS, one connection open and one query tab | ≤ 150 MB |
| First rows of a large `SELECT` visible after the server starts sending (localhost) | ≤ 150 ms |
| Scrolling the 1,000,000-row result | average frame time < 16 ms |
| Memory for 1,000,000 rows × 20 mixed columns fetched in full | reported; compact storage, no `String` per cell |

Fixtures: `analytics.big_table` (PostgreSQL) and its MySQL counterpart have 1,000,000 rows; check their
column count in `tests/fixtures/*/03_big.sql`. For "× 20 mixed columns" use a query that widens it, e.g.
PostgreSQL `SELECT g AS id, g * 2 AS n2, (g % 97)::numeric / 7 AS dec, md5(g::text) AS h, now() - (g ||
' s')::interval AS ts, g % 2 = 0 AS flag, gen_random_uuid() AS u, jsonb_build_object('k', g) AS j, … FROM
generate_series(1, 1000000) g` up to 20 columns (write it once in `docs/BENCH.md` and in the bench code).

## Part 1 — Instrumentation: a bench mode (app) — `opus`

Files: new `crates/kerno/src/bench.rs`; `main.rs`, `workspace.rs`, `query/tab.rs`, `query/grid.rs` (hooks
only). Everything behind the environment variable `KERNO_BENCH`; without it nothing changes and nothing is
measured (no cost in normal runs). Results are printed to stdout as one JSON line per measure and the app
quits by itself.

1. `KERNO_BENCH=startup`: record `Instant` at the top of `main` (and the process start time from
   `sysctl`/`proc_pidinfo` if easy, else note that the measure starts at `main`), then the first frame
   presented with the workspace drawn (`window.on_next_frame` after the first render) and the first frame
   after which input is handled; print `{"bench":"startup","main_to_first_frame_ms":…}`; quit.
   The external measure (process spawn → window on screen) is taken by the script of Part 3.
2. `KERNO_BENCH=first_rows` with `KERNO_BENCH_CONNECTION=<name>` and `KERNO_BENCH_SQL=<statement>`: connect
   to the saved connection (password from the scratch secret store: `KERNO_SECRET_STORE=memory` cannot hold
   one across runs, so accept `KERNO_BENCH_PASSWORD` in bench mode only, read once, never logged), open a
   query tab, run the statement, and measure: statement sent → first `ExecEvent::Rows` received → first
   frame in which the grid shows rows; then fetch all and measure total time and rows per second, RSS
   before and after (`ps -o rss= -p <pid>` or `mach_task_basic_info`), and
   `ResultStore::memory_bytes()`. Print and quit.
3. `KERNO_BENCH=scroll`: after fetch-all of the 1M-row result, scroll the grid programmatically from top to
   bottom in steps (`TableState::scroll_to_row`) for about 10 seconds, one step per frame
   (`window.request_animation_frame` / `on_next_frame`), record each frame's duration (time between
   presented frames) and print count, average, p50, p95, p99, max. Also a horizontal pass
   (`scroll_to_col`).
4. A debug overlay is not required; the bench mode is the instrument (CLAUDE.md allows either).

Unit-test what is pure (percentiles); the modes themselves are exercised by Part 3.

**Done (2026-11-13).** `crates/kerno/src/bench.rs` (modes `seed`, `startup`, `first_rows`, `scroll`; refuses
without `KERNO_DATA_DIR` and `KERNO_SECRET_STORE=memory`; 180 s watchdog), hooks in `main.rs`, `query/tab.rs`
(sent, columns, first rows, finished), `query/grid.rs` (sort done, first cell of a frame), `workspace.rs`
(`open_query` made public); `first_rows` also reports idle RSS, fetch all, `memory_bytes` per cell and the
client-side sort (`hash` column); `scripts/bench.sh` (Part 3's script) runs it. Left: the frame "work" time is
measured from the first grid cell drawn to the next-frame callback, which includes the wait for the
drawable, so it is an upper bound; the process start before `main` is only in the script's spawn-to-line
number. `docs/BENCH.md` is not written (Part 3).

## Part 2 — Find and fix what is slow — `opus` (one agent per finding when independent)

Measure first (Part 3's script), then fix only what misses a target or is clearly wasteful. Known suspects,
in the order to check them:

1. **Per-cell work in `Grid::render_td`** (`crates/kerno/src/query/grid.rs`): each visible cell builds a
   context-menu wrapper (an element id string is formatted per cell per frame), a mouse listener, and
   formats its text with `format::display`. If scrolling misses 16 ms: (a) attach the context menu once per
   row or once on the table and resolve the row from the mouse position; or keep per-cell but avoid the
   `format!` (precomputed ids); (b) cache the formatted text of the visible window between frames (a small
   LRU keyed by `(row, column)`, cleared on new rows / sort / edit); (c) make sure `SharedString` creation
   does not copy twice.
2. **`ResultStore` memory** (`crates/kerno-core/src/result.rs`): batches hold cell bytes in one arena plus
   offsets. Report bytes per cell for the 1M × 20 result; if offsets dominate (8 bytes per cell), use `u32`
   offsets per batch. No `String` per cell anywhere on the path (check the drivers' row decoding:
   `kerno-postgres/src/session.rs`, `kerno-mysql/src/session.rs` push into `BatchBuilder` directly).
3. **Startup**: what runs before the first frame (`main.rs`): storage open and migrations, settings, fonts
   (embedded Inter and JetBrains Mono: registered once), theme, keymap file, logging setup, the Tokio
   runtime. Anything slow moves after the first frame or onto `bridge::spawn_blocking`. Restored tabs must
   not open sessions before the window shows (they do not connect by themselves today; verify).
4. **First rows**: the driver's batch size and the first-batch flush (`exec.rs`, drivers): the first batch
   should be sent after a small number of rows or a few ms, not when a 1,000-row batch is full, if the
   server is slow to produce rows; measure with `SELECT … FROM generate_series` and with `pg_sleep` between
   rows (`SELECT g, pg_sleep(0.001) FROM generate_series(1, 5000) g`).
5. **Idle RSS**: with one connection and one tab. If above 150 MB look at glyph atlases, the embedded
   fonts, the SVG logos rasterised at large sizes, the Tokio runtime's thread stacks (3 workers), the
   navigator tree of large schemas.
6. **Statement splitting** is quadratic (see `docs/plans/M5.md` Part 3) — must be fixed by now; verify
   with a 5 MB script pasted in the editor: typing stays responsive (completion and statement-at-cursor
   run per keystroke on the statement only).
7. **Client-side sort of 1M rows** runs off the UI thread already; report its time.

Every fix comes with the before / after numbers in the report and keeps all tests green.

**Done (2026-11-13), measured on a busy machine (load 5–10): indicative, the clean figures are Part 3's.**

- **Startup.** Traced with `Instant` marks and an Instruments time profile. Kerno's own work before the
  first frame is about 2 ms of setup plus 7–15 ms for the first draw. A control build whose workspace
  draws an empty `div` costs only 20–35 ms less at the median (first frame 247 vs 268 ms, interactive 439
  vs 473 ms over 8 runs each). With a restored query tab the gap is 50–60 ms, of which about 30 ms is
  `tree_sitter::Query::new` for the SQL highlight query: the kit compiles it again for every editor and
  holds a 16 MB scratch while doing so; only the visible tab pays it.
- **Where the rest goes, outside Kerno (GPUI, the kit, AppKit):**
  - about 100 ms of platform start;
  - about 30 ms of font listing, run by `gpui_component::init`;
  - `set_menus`, about 20 ms (up to 190 ms on a new binary: AppKit loads Writing Tools);
  - about 55 ms for the NSWindow and the Metal renderer.
- **The 140–250 ms "second frame" is not a frame.** Between the first presented frame and the next
  display-link tick the main thread is mostly blocked in AppKit app activation (text input context,
  menu bar, Core Animation commit); no Kerno code runs there.
- **Startup, not changed.** Prewarming the font list on a thread and activating the app early were
  tried; neither showed a gain above the noise.
- **Startup, instrument.** The first launch of a freshly built binary took 1.7–2.1 s: `bench.sh` now
  launches once, untimed, before measuring.
- **Idle memory.**
  - The log channel preallocated 128,000 lines (4.1 MB): capped at 1,024 lines, still lossy (`logging.rs`).
  - `img()` rasterised SVG logos at twice their own size and kept them: 5.5 MB of pixels plus a 5.7 MB
    texture for a PostgreSQL logo drawn at 16 px. `engine_logo::svg_image` rasterises each logo and brand
    file at the pixels it covers, once per size (`engine_logo.rs`, `brand.rs`). Files unchanged; captures
    checked light and dark.
  - Result: heap 24.0 → 13.2–14.2 MB; graphics (IOAccelerator) 16 → 11 MB.
  - Idle footprint is about 183–199 MB at the bench's sample point. The floor:
    - 90 MB of GPU memory and 48 MB of IOSurface: three full-window drawables;
    - the kit's freed 16 MB query scratch.
- **Idle RSS (126–151 MB) is not a stable figure here.** It drops by 30–50 MB in the following seconds
  with nothing freed: the system compresses pages under memory pressure. `first_rows` now also reports
  `idle_footprint_mb` and `footprint_after_mb` (macOS `footprint`).
- **Result memory.** Offsets were already `u32` per batch.
  - **Before:** `memory_bytes` counted capacity, and each 1,024-row batch regrew its buffers by doubling,
    then `shrink_to_fit` copied them. After a 1M × 20 fetch, malloc held 366.6 MB for 340 MB of rows: 10%
    fragmentation from the freed growth buffers. The RSS swing (252–539 MB) was compression: vmmap showed
    378 MB swapped out.
  - **Now:** the builder keeps scratch buffers from batch to batch; past 4 MB they are released, so a
    paused statement never holds a large one. `finish` copies them into exact-size `Box<[T]>`, so a batch
    has no slack by type. `memory_bytes` is lengths plus the store's bookkeeping.
  - **Measured:** 340.1 MB, 17.0 B/cell (12.9 data, 4 offset, 0.125 NULL bit). Footprint after the fetch
    went from 628–633 MB to 560–577 MB.
  - No `String` per cell on the PostgreSQL path. MySQL: `mysql_async` hands each row over as one `Vec<u8>`
    per cell, dropped once the row is copied into the batch.
  - Tests: `a_finished_batch_holds_exactly_its_cells`, `a_scratch_grown_by_large_values_is_released`,
    `store_memory_is_its_rows_plus_bookkeeping`.
- **Bench changes.**
  - The scroll mode's `work_ms` is removed, with the `bench::cell` hook in `query/grid.rs`: it timed the
    wait for the next frame slot.
  - `bench.sh` prints the load average of each run.
  - Known gap: a result too small for the background sort never marks `sorted`, so `first_rows` on a few
    rows ends at the watchdog. Use the 1M-row tables.

## Part 3 — Measure and write `docs/BENCH.md` — `sonnet` drives, main session reviews

New `scripts/bench.sh` (uses `nice` only for the build, **not** for the measured runs; checks `uptime`
first and refuses to measure when the load average is above 4; builds `--release`; runs each mode 5 times
and keeps the median; uses a scratch data directory seeded with one saved connection to `kerno-postgres`
and one to `kerno-mysql` — look at how the UI tests save a connection (`storage.save_connection`) and write
a tiny `kerno --bench-seed`-style helper or a test-support binary if needed; never the user's real data
directory). Cold start from outside: time from `spawn` to the first JSON line, plus the app's own number.
RSS with `ps -o rss=`.

`docs/BENCH.md`: machine (model, chip, RAM, macOS version: `sysctl -n machdep.cpu.brand_string`,
`sw_vers`), date, commit, build flags, the method for each number (what starts and stops the clock), the
exact statements, the table of results (median of 5, with min–max) against the targets, PostgreSQL and
MySQL where it applies, the 1M × 20 memory figure (RSS delta and `memory_bytes`, bytes per cell), the
client-side sort time, export / import throughput from milestone 8 (rows per second), and a short "what
was changed to get here" list. A target that is missed is written as missed, with the cause and what would
fix it — and then fixed in Part 2 until it passes.
