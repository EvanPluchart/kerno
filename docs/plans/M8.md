## Part 1 — Export to a file (core + app) — `opus`

Core, new `crates/kerno-core/src/export_file.rs` (or extend `export.rs` if it stays readable):

```rust
pub enum Encoding { Utf8, Utf8Bom, Utf16Le, Latin1 }     // Latin1: characters outside it are written as '?'
pub struct ExportJob { pub sql: String, pub format: ExportFormat, pub encoding: Encoding, pub path: PathBuf }
pub struct ExportProgress { pub rows: u64, pub bytes: u64 }
/// Runs `job.sql`, writes every row to the file as it arrives. Reports progress about every 5,000 rows
/// through `progress`. Stops when `cancel` is set (and cancels the statement); the partial file is removed.
pub async fn export_to_file(session: Arc<dyn Session>, job: ExportJob,
    progress: impl Fn(ExportProgress) + Send + 'static, cancel: Arc<AtomicBool>) -> Result<ExportProgress>;
```

File writes are blocking: do them with `tokio::task::spawn_blocking` per batch or a dedicated writer thread
fed by a bounded channel, so the Tokio workers are not blocked and memory stays flat (the 1M-row fixture
`analytics.big_table` must export with a few MB of resident memory growth: assert on rows written and that
no `ResultStore` is built). Write to `path.tmp` then rename. Tests: every format round-trips a result with
NULLs, quotes, newlines, unicode, binary; delimiter / header / NULL text / line ending / encoding options;
cancel removes the file; an error (bad SQL, unwritable path) removes it and says why; the 1M-row export
writes 1,000,000 lines (PostgreSQL and MySQL).

App, new `crates/kerno/src/export_dialog.rs` + wiring in `data/tab.rs`, `query/tab.rs`, `navigator`
(`Action::Export` "Export…" on tables and views), `actions.rs` (`ExportData` command "Export…", group
"Data"), `workspace.rs`:

- Dialog: format (CSV, TSV, JSON array, NDJSON, SQL INSERT, Markdown), options that apply to the format
  (delimiter, header, NULL text, line ending, encoding; target table name for INSERT, prefilled), then
  "Choose file…" (`cx.prompt_for_new_path`, see `save_file_as` in `workspace.rs`), then a progress row
  ("123,000 rows · 14 MB"), Cancel, and at the end "Exported 1,000,000 rows to <path>" with "Show in Finder"
  (`cx.reveal_path`). It runs on a **session of its own** (`connections.open_session`), so the tab stays
  usable.
- Sources: a table or view (the data tab's toolbar "Export…" and the navigator: `SELECT * FROM t` with the
  tab's current filter and sort, without `LIMIT`; say in the dialog "all rows matching the filter"), a query
  result (the result footer "Export…": re-runs the statement of that result — say so; a statement that
  writes is not re-run, the button is absent for results of DML).
- Tests: export a table to CSV and to JSON through the dialog with the path prompt simulated
  (`cx.simulate_new_path_selection`, see the SQL file test), file content checked; cancel a long export

## Part 2 — Import CSV (core + app) — `opus`, can run with Part 1

Core, new `crates/kerno-core/src/import.rs` (no new dependency unless parsing needs it: a CSV reader with
quotes, escaped quotes, embedded newlines, a chosen delimiter and CRLF is ~120 lines; if the `csv` crate is
preferred, check its licence with `cargo deny check` and record it in DECISIONS):

```rust
pub struct CsvOptions { pub delimiter: char, pub header: bool, pub null_text: String, pub encoding: Encoding }
pub struct CsvPreview { pub headers: Vec<String>, pub rows: Vec<Vec<String>>, pub guessed: Vec<TypeKind> }
pub fn preview(path: &Path, options: &CsvOptions, rows: usize) -> Result<CsvPreview>;   // first N rows
/// Guess from the sampled values: Integer, Decimal, Boolean, Date, DateTime, Uuid, Json, else Text.
pub fn guess_kind(values: &[&str], null_text: &str) -> TypeKind;
pub enum Target { Existing(TableRef), New { table: TableRef, columns: Vec<(String, String)> } } // name, SQL type
pub struct ImportJob { pub path: PathBuf, pub options: CsvOptions, pub target: Target,
    pub mapping: Vec<Option<String>>,    // per CSV column: target column, or None to skip
    pub batch_rows: usize }              // default 500
pub struct ImportReport { pub inserted: u64, pub failed: Option<ImportFailure> }
pub struct ImportFailure { pub line: u64, pub message: String }
pub async fn import_csv(session: Arc<dyn Session>, columns: Vec<ColumnInfo>, job: ImportJob,
    progress: impl Fn(u64) + Send + 'static, cancel: Arc<AtomicBool>) -> Result<ImportReport>;
```

One transaction: `START TRANSACTION`, `CREATE TABLE` first for a new table (on MySQL DDL commits
implicitly: create, then the inserts in a transaction, and drop the new table if the import fails; say so),
multi-row `INSERT INTO t (cols) VALUES (…), (…)` per batch with `dialect.literal(&CellValue, &ColumnInfo)`
(the NULL text becomes `CellValue::Null`), `COMMIT`; any error → `ROLLBACK`, report the CSV line of the
failing batch (on failure, retry that batch row by row inside a savepoint on PostgreSQL / plainly on MySQL
to find the line, then roll everything back). The SQL type per guessed kind comes from a new
`Dialect::type_for(kind: TypeKind) -> &'static str` (PostgreSQL: bigint, numeric, boolean, date,
timestamptz, uuid, jsonb, text; MySQL: bigint, decimal(38,10), tinyint(1), date, datetime, char(36), json,
text). Tests: parser edge cases; type guessing; import into an existing table with a mapping that skips and
reorders columns; into a new table; a bad value at line N rolls everything back and reports N; 100,000 rows
import (generate the file in the test) on PostgreSQL and MySQL; cancel rolls back.

App, new `crates/kerno/src/import_dialog.rs`; entry points: navigator "Import CSV…" on a table (existing
target) and on the Tables folder / schema (new table), palette command "Import CSV…". Steps in one dialog:
choose file (`cx.prompt_for_paths`) → options (delimiter auto-detected among `, ; \t |` from the first
lines, header, NULL text, encoding) with a live preview grid of the first 50 rows → mapping table (CSV
column → target column dropdown or "skip"; for a new table: column name and type, prefilled from the
header and the guess) → "Import" through `sql_confirm` (shows the `CREATE TABLE` if any and the first
`INSERT` with "… and N more rows") → progress, cancel → report ("12,000 rows imported" or "Nothing was
imported: line 418: invalid input syntax for type integer…"). Read-only connections cannot import. After a
success the navigator's Tables folder and an open data tab of that table are refreshed.
Tests: import into an existing table and into a new one through the dialog; error report; read-only refused.
Captures: `m8-import-preview-light.png`, `m8-import-mapping-dark.png`, `m8-import-error-light.png`.

## Part 3 — Backup and restore through the client tools (core + app) — `opus`

Core, new `crates/kerno-core/src/tools.rs`:

```rust
pub enum Tool { PgDump, PgRestore, Psql, MysqlDump, Mysql }            // MariaDB: mariadb-dump / mariadb too
pub fn find(tool: Tool) -> Option<PathBuf>;     // $PATH, then /opt/homebrew/bin, /usr/local/bin,
                                                // /opt/homebrew/opt/{libpq,mysql-client,mariadb}/bin,
                                                // /Applications/Postgres.app/Contents/Versions/latest/bin, /usr/bin
pub struct ToolCommand { pub program: PathBuf, pub args: Vec<String>, pub env: Vec<(String, String)>,
                         pub stdin: Option<PathBuf>, pub stdout: Option<PathBuf> }
impl ToolCommand { pub fn display(&self) -> String }   // what the user is shown: no secret, env names only
pub fn backup_command(tool_path: &Path, params: &ConnectParams, options: &BackupOptions) -> Result<ToolCommand>;
pub fn restore_command(tool_path: &Path, params: &ConnectParams, options: &RestoreOptions) -> Result<ToolCommand>;
pub async fn run(command: ToolCommand, on_line: impl Fn(String) + Send + 'static, cancel: Arc<AtomicBool>)
    -> Result<std::process::ExitStatus>;       // tokio::process, stderr and stdout lines streamed, kill on cancel
```

- The password never goes on the command line: `PGPASSWORD` / `MYSQL_PWD` in the child's environment only
  (`display()` shows `PGPASSWORD=•••`). Host, port, user, database from `ConnectParams`; through an SSH
  tunnel the tool connects to the tunnel's local port (look at how `Connector` exposes it; if it does not,
  expose `local_endpoint()`), TLS mode mapped to `PGSSLMODE` / `--ssl-mode`.
- `BackupOptions`: database, output file, format (PostgreSQL: plain SQL or custom `-Fc`; MySQL: SQL),
  schema only / data only, selected tables (optional). `RestoreOptions`: input file; PostgreSQL plain →
  `psql -f`, custom → `pg_restore -d`; MySQL → `mysql < file` (stdin from the file).
- Tests: `find` with a fake `$PATH`; exact command lines for each case; `display()` never contains the
  password; `run` streams lines and reports a non-zero exit, with a small shell script as the program;
  cancel kills the child. Integration (skipped with a clear message when the binary is missing): `pg_dump`
  of the `kerno_other` test database to a temp file then `psql` restore into a scratch database
  `kerno_test_restore` created and dropped by the test, tables compared. The same for `mysqldump` / `mysql`
  when present.

**The core half is done** (`kerno_core::tools`, commit "backup and restore through the installed client
tools"; read the module before the dialog). Facts found: `mysql-client` **is** installed on the development
Mac (keg-only, `/opt/homebrew/opt/mysql-client/bin`, found through the fallback directories), so the MySQL
round trip runs for real and the owner need not be asked; only the MariaDB-named binaries are absent.
`find()` returns the first match, and on this Mac that is `pg_dump` 14, which refuses a PostgreSQL 17 server
("server version mismatch") while `/opt/homebrew/opt/libpq/bin` holds 18. For the dialog: add
`tools::find_all(tool) -> Vec<PathBuf>` and a `version(path)` helper (parse `--version`), and choose by
default the first PostgreSQL tool whose major version is at least the server's (`session.server()`); show
the version and say so when none is recent enough. Not passed to the tools: `ConnectParams.options`. A MySQL
restore is not atomic (say so in the confirmation); MySQL through a tunnel with verify-full checks the name
`127.0.0.1` (refuse that combination with a clear message).

**Part 3b — a restored SQL file must not run local commands unasked (`opus`, core `tools.rs`; before the
dialog ships).** Security review of the commit: `psql --file` and `mysql < file` execute the client
commands a file contains (`\!`, `\copy … program`, `\o |…`, `\i`, `\w`, `\g |…` in psql; `system` / `\!`,
`source` / `\.`, `tee` / `\T`, `pager` / `\P` in mysql), so a dump from an untrusted source can run programs
on the user's machine. Fix, in this order:
1. Use the tool's own sandbox when its version has one, verified by a round trip of a dump that holds
   routines and triggers (mysqldump writes `DELIMITER`, which must keep working): MariaDB client
   `--sandbox`; MySQL client `--commands=OFF` (check `mysql --help` and the manual of the installed version
   for the exact option and since when it exists; add a `version(path)` helper).
2. Everywhere else (psql always; mysql clients without the option): scan the file before running
   (streaming, not loading it whole) for those client commands — in psql files, everywhere including
   `COPY … FROM stdin` data, treating `\\` as an escaped pair so genuine data never matches — and refuse
   with `Error::Config` naming the first line and command found, unless `RestoreOptions::allow_client_commands`
   is set. `\connect`, `\restrict`, `\unrestrict`, `\encoding` and the `\.` that ends COPY data are what
   pg_dump writes and are allowed.
3. The custom format (`pg_restore`) holds no client script: unchanged.
4. Tests: a file with `\! touch <tempdir>/pwned` (psql) and with `system touch …` / `\! …` (mysql) is
   refused and the marker file does not exist; with the opt-in it is passed through (assert on the command,
   do not run it); genuine dumps of the fixture databases (with COPY data holding backslashes, and MySQL
   routines) still restore; false positives are named so the user can decide.
The dialog (below) shows the refusal with its line, offers the opt-in as an explicit checkbox ("This file
runs commands on this computer: …. Run it anyway"), and its confirmation always says that a SQL file is a
script run by the client tool.

App, new `crates/kerno/src/backup_dialog.rs`; entries: navigator "Back up…" / "Restore…" on a database
node (PostgreSQL) or database (MySQL), palette commands. The dialog shows the detected binary and its
version (`--version`), "Choose…" to pick another path (stored in settings per tool:
`settings.tool_paths`), the options, the **command that will run** (from `display()`), then a log pane with
the tool's output streaming, Cancel, and the exit status. Missing binary: a message that says which binary
is needed and how it is usually installed (`brew install libpq` / `mysql-client` / the distribution
package), and the path chooser; nothing else. Restore is destructive: `sql_confirm`-style confirmation
naming the database and the file (production asks twice; read-only connections cannot restore).
Tests: the dialog with a fake binary (a script written by the test, chosen as the tool path): command
shown without the secret, output streamed into the log, exit status; the "missing binary" state.
Captures: `m8-backup-light.png`, `m8-backup-missing-tool-light.png`, `m8-restore-confirm-dark.png`.

**MySQL tools on this Mac**: present (see above); nothing to ask the owner.
