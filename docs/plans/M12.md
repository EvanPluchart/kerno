## K1 — Quitting asks when a transaction or pending work would be lost (C15)

**Now.** `main.rs:188` binds `Quit` to `cx.quit()`; `main.rs:208-212` quits when the last window closes. An
open transaction, pending data edits, unsaved script text in a file tab: all dropped without a word (the
server rolls back when the socket closes). The update install already asks through
`Workspace::end_then` (`workspace.rs:4343`; `ui_tests::updates::quitting_to_update_asks_first_and_declining_keeps_the_download`).

**Wanted.** Cmd+Q, the Quit menu item and the window's close button run the same question as closing every
tab at once: `end_then("Quit", <all open tabs>, Then::Quit, …)`. Nothing to lose: quit at once (no dialog).
Something to lose: the dialog of `tabs::end_question` lists it ("2 tabs: a transaction on “orders” (open 4
min), pending edits on shop.customers"), with the buttons and the default of `tabs::end_question` as they
are (Enter never confirms a loss, `docs/plans/README.md`): roll back or discard and quit, or Cancel. Rolling
back sends `ROLLBACK` on each open transaction before quitting (the existing `end_then` path does it), with a
3 s limit per session so a dead server does not hold the quit. The update install keeps its own wording.

**Files.** `main.rs`: route `Quit` to the workspace (`cx.on_action` finds the workspace window and dispatches a
workspace action; if no window exists, quit). `workspace.rs`: a `quit` handler calling `end_then` with every
open tab; `on_window_should_close` (GPUI `Window::on_window_should_close`, read its signature in the pinned
gpui) returns `false` and runs the same handler. A `Then::Quit` variant if `Then` has none (look at how the
update path ends the app and reuse it).

**Tests** (`ui_tests/critique.rs`, PostgreSQL and MySQL):
- `quitting_with_an_open_transaction_asks_and_cancel_keeps_it` (C15): manual tab, `insert into
  kerno_ui_quit.t values (1)`, dispatch `Quit`: the dialog names the tab; Cancel: the app is still running,
  `tx_state() == Open`.
- `quitting_with_nothing_to_lose_quits_at_once`.
- `roll_back_and_quit_rolls_back`: confirm; on the server (`on_server`), the row is absent and no session of
  the test's marker holds a transaction.
- Closing the window takes the same path (one test through `on_window_should_close`).

**Acceptance.** No path quits with an open transaction or pending edits without the question. **Capture:**
the quit dialog with a transaction open (`m12-quit-question-{light,dark}.png`).

Done: `Workspace::quit` runs `end_then`'s question ("Quit Kerno?") over every open tab, then `cx.quit()`; the
workspace handles `Quit` when it is on the keyboard's path, and `main.rs` registers the app-wide one
(`workspace::handle_quit`) after the window opens: it hands `Quit` to the workspace (deferred, the window is in
use during a dispatch) and quits directly only without a window. `on_window_should_close` returns `false` and runs the same `quit`. `Then`
is a boxed closure, not an enum: no variant was needed. When quitting, each `ROLLBACK` is limited to 3 s
(`QUIT_ROLLBACK_LIMIT`, a Tokio timeout in `QueryTab::finish_transaction`) and one that fails or gets no answer
does not hold the quit (the server rolls back when the socket closes); a failed `COMMIT` still stops it. The
update install keeps its own wording and its unlimited wait. Unsaved file text is not asked about: the stored
tabs keep it (`TabSnapshot::Query { sql, unsaved }`). A table form with changes not applied (`Loss::Form`) is
closed with the app, so quitting asks about it too (`tabs::quit_question`; disconnecting still does not, the
form survives it). A second Quit while the question is on screen does not ask twice (`Workspace::quit_question`,
a token the dialog holds). Not covered: the Dock's Quit, logout and SIGTERM send `terminate:` straight to
AppKit (gpui has no `applicationShouldTerminate`), so they quit without asking (`docs/ROADMAP.md`, limits). Tests:
`tabs::tests::ending_a_session_asks_once_for_its_transactions_and_pending_changes` (the form),
`ui_tests::critique::{quitting_with_an_open_transaction_asks_and_cancel_keeps_it,
quitting_with_nothing_to_lose_quits_at_once, roll_back_and_quit_rolls_back,
closing_the_window_asks_as_quit_does}` on PostgreSQL and MySQL, and `quitting_from_a_dialog_asks_too` (the
app-wide handler, a dialog having the keyboard, one question for two Quits) on PostgreSQL.

## K2 — Every write can be cancelled; the first page of a table too (C3)

**Now.** No cancel for the data tab's Apply (`data/tab.rs:1350`: `cancel` acts only while loading or
counting), the structure editor's Apply (`structure/editor.rs:983-1013`), navigator Drop / Truncate / Rename
/ Create (`navigator/view.rs:2185`, task detached at 2209). Each waits forever on a lock held by another
session (PostgreSQL: a queued `ALTER` then blocks every reader of the table); closing the tab leaves the
statement running (`bridge.rs:35-36`: dropping a task does not stop the work). A cancel by dropping the future
would not help: inside a transaction block the PostgreSQL session skips the server cancel on purpose
(`kerno-postgres/src/session.rs:420-431`); an explicit `session.cancel()` stops it, block and all. Also, a
table opened for the first time shows Cancel while "Loading rows…" but `DataTab::cancel` does nothing:
`self.session` is set only in `show()` (`data/tab.rs:890`).

**Repro.** `kerno-postgres`: session A `begin; lock table kerno_ui_k2.t in access exclusive mode;`. In
Kerno: edit a cell of `kerno_ui_k2.t`, Apply → "applying…" forever, Cmd+. does nothing. Same with the
structure editor (add a column) and navigator Truncate.

**Wanted.**
- Data tab: keep the apply's session in the tab (`self.applying_session`) and have `cancel` call
  `session.cancel()` while `applying`; the apply then fails with the cancel, rolls back (it is one transaction,
  `sql/edits.rs:224`), keeps the pending edits, and says "Cancelled: nothing was changed. The pending changes
  are kept." (not "Check the filter").
- Data tab first page: store the session in `self.session` as soon as `open_session` returns, before the page
  query starts (move the assignment from `show()` to the load path), so `cancel` reaches it. A cancelled page
  says "Cancelled." with a Reload button, not the filter advice of `data/tab.rs:181-187`.
- Structure editor: a **Cancel** button beside the "applying" state and Cmd+.; keeps the session of
  `run_statements` in the editor and calls `session.cancel()`; on PostgreSQL the transaction rolls back
  ("Cancelled: nothing was changed."); on MySQL (DDL commits per statement) "Cancelled at statement N of M;
  the statements before it were applied." (reuse the existing partial-apply wording at
  `structure/editor.rs:1044-1056`).
- Navigator writes: run in a short-lived "running" state on the node (spinner and "Dropping…" on the row) with
  a **Cancel** entry in the node's context menu and in a notification that stays while it runs ("Dropping
  shop.t… Cancel"); Cancel calls `session.cancel()`.
- Cmd+. (`workspace.rs:2994-3001`) also reaches the active structure tab.
- Closing a tab that is applying cancels first (explicit `session.cancel()` in the tab's drop/close path),
  so nothing keeps running in the background.

No `lock_timeout` is set: a user may legitimately wait; what was missing is the way out. Record that choice
in `docs/DECISIONS.md`.

**Tests** (`ui_tests/critique.rs`, a `Locker` helper beside `Sleeper` that holds `LOCK TABLE` from a session
of the test; PostgreSQL, and MySQL with `LOCK TABLES … WRITE`; wait for the waiting statement with
`running_on_server(engine, marker)` before cancelling, as `docs/plans/README.md` says):
- `a_data_apply_behind_a_lock_is_cancelled_and_keeps_the_edits` (C3)
- `a_structure_apply_behind_a_lock_is_cancelled`
- `a_navigator_truncate_behind_a_lock_is_cancelled`
- `the_first_page_of_a_table_behind_a_lock_is_cancelled` (open the tab for the first time while locked;
  assert the server statement is gone: no row in `pg_stat_activity` with the marker)
- `closing_a_tab_that_applies_stops_the_statement`

**Acceptance.** Every write path has a visible cancel that stops the statement on the server; no statement
of a closed tab keeps running. **Captures:** structure editor applying with Cancel; navigator row "Dropping…".

Done: `DataTab::cancel` acts while applying too (the apply already runs on `self.session`: no second field
was needed); `cancel_requested` makes a cancelled apply say "Cancelled: nothing was changed. The pending
changes are kept." and a cancelled read a new `State::Cancelled` ("Cancelled: the rows were not read", Reload);
the load stores its session as soon as `open_session` returns, and a Cancel that came while it opened stops it
there. `TableEditor` keeps `applying_session` and a cancel flag read between statements, shows "Applying…" with
`editor-cancel`, and its `cancel` is reached by `Workspace::cancel_query` (Cmd+., status bar) and by
`close_tab_at`; `DataTab::close_session` cancels before closing when busy. Navigator Drop/Rename/Create run on
a session of their own (`Navigator::execute`, D-077): a `Write` per statement, "Dropping table t…" on the row
in place of its hint, "Cancel the running statement" first in its menu, a notification with Cancel
(`navigator-write-cancel`) removed when it ends. No spinner (text, as elsewhere). The plan was wrong on three
points: Truncate goes through the maintenance dialog, which already had a cancel on the server (its test is
kept as a pin, a Drop test covers the new path); a data tab's apply was already stopped when its tab closed
(`close_session` → both drivers' `close()` cancel a busy statement): what kept running was a table form's apply
and a first page; a dropped task never reaches the driver at all (`bridge::spawn` detaches the Tokio task), the
PostgreSQL in-block rule only matters for `exec` consumers that drop their execution. On PostgreSQL the first
statement of a first page to wait is the catalog read of the table's indexes (`pg_get_indexdef`), by oid: the
tests wait for a session blocked by the test's own locker (`pg_blocking_pids`, MySQL
`sys.schema_table_lock_waits`), not for a marker in the text. Tests: `ui_tests::critique::{
a_data_apply_behind_a_lock_is_cancelled_and_keeps_the_edits, a_structure_apply_behind_a_lock_is_cancelled,
a_navigator_truncate_behind_a_lock_is_cancelled, a_navigator_drop_behind_a_lock_is_cancelled,
the_first_page_of_a_table_behind_a_lock_is_cancelled, closing_a_tab_that_applies_stops_the_statement}` on
PostgreSQL and MySQL, with a `Locker` helper; `a_slow_page_is_cancelled_and_the_tab_stays_usable` now expects
"cancelled". Not covered (K15 or later): the structure tab's "Set comment", the FDW dialog, the admin tab's
cancel/terminate, a cancel that lands between two statements of a data apply (`apply_edits` sends the next one;
the Cancel button stays offered); reads that wait behind the same lock: the table form's own load and the
structure tab's (on PostgreSQL `pg_get_indexdef` waits) show "running…" in the status bar, but its Cancel does
nothing there (`TableEditor::cancel` acts only while applying) and closing such a tab leaves the read waiting.

## K3 — A query tab shows the database and schema its session is really in (C6)

**Now.** The tab's database and schema are applied once when its session opens (`query/tab.rs:1257-1288`:
`open_session(target.database)`, then `SET search_path TO <schema>, public`). After `USE b` (MySQL) or `SET
search_path TO other` (PostgreSQL) the picker and status bar still show the target
(`workspace/toolbar.rs:406-413`, `query/tab.rs:818-824`). Worse, any rebuild of the tab's session
(auto-reconnect `query/tab.rs:1061`/`1106`, read-only toggle, isolation change) silently returns to the
target: the user believes they are in `b`, the next statement runs in `a`. The MySQL driver already follows
`USE` (`kerno-mysql/src/session.rs:430-433`, `Session::database`); the app never reads it for the tab.
`\c` is sent to the server as SQL and fails there (fine: psql meta-commands are not SQL).

**Wanted.** The session's state wins and becomes the tab's target:
- `kerno-core/src/driver.rs` `Session`: add `fn schema(&self) -> Option<String>` beside `database()`
  ("the first schema of the search path on PostgreSQL; `None` where the engine has none").
- `kerno-postgres/src/session.rs`: after a statement for which `touches_session_state` is true (write a
  PostgreSQL one as the MySQL driver has at `kerno-mysql/src/session.rs:497`: `SET [SESSION|LOCAL]
  search_path`, `SET SCHEMA`, `RESET search_path`, `RESET ALL`, `DISCARD ALL`), read `select
  current_schema()` and keep it; `schema()` returns it.
- `query/tab.rs`: after each statement, if `session.database()` or `session.schema()` differs from the
  target, update `target.database` / `target.schema` (the tab's stored snapshot follows, so a restart and a
  reconnect come back to where the user was) and say it in the messages panel: "Now in database b (USE)."
  The picker then shows the truth.
- A `SET LOCAL search_path` inside a transaction is undone at commit or rollback: after `COMMIT`/`ROLLBACK`
  read it again (the same hook covers it if `touches_session_state` also matches `COMMIT`, `ROLLBACK`,
  `END`, `ABORT` when the previous statement set it; simpler: always re-read after a transaction ends).

**Tests.**
- Driver tests: `kerno-postgres/tests/session.rs` `the_schema_follows_set_search_path` (C6), including `SET
  LOCAL` then `ROLLBACK`; `kerno-mysql/tests/session.rs` already covers `USE`: check, add if absent.
- UI (`critique.rs`): `use_in_a_tab_moves_its_picker_and_survives_a_reconnect` (MySQL and MariaDB: run `use
  kerno_ui_k3_b`, the picker shows `kerno_ui_k3_b`; kill the tab's backend with `on_server("kill <id>")`, run
  `select database()`: the result is `kerno_ui_k3_b`), and the PostgreSQL twin with `set search_path`.
- Unit test for the PostgreSQL `touches_session_state`.

**Acceptance.** No sequence of statements, reconnects or toggles makes the tab run somewhere other than what
its picker shows. **Capture:** a tab after `USE`, picker updated, message shown.

Done: `Session::schema()` (default `None`); `PgSession` reads `current_schema()` at connect (in the identity
query, no extra round trip) and again, on the link it holds, after a request `touches_session_state` matches:
a statement starting with `SET` (search path, schema, role and session authorization, which move `$user`),
`RESET`, `DISCARD`, `DO`, `CALL`, or ending a transaction (`COMMIT`, `ROLLBACK` including `TO SAVEPOINT`,
`END`, `ABORT`, `PREPARE`: a plain `SET` inside a block that rolls back is undone too, not only `SET LOCAL`),
or any `set_config` call; not after a closed or let-go statement; a failed read (aborted block) keeps the last
value; NULL gives `None`. `QueryTab` remembers where its session was when it was installed (after its own
`SET search_path`) and, after each statement and after Commit / Roll back (`finish_transaction`, idle rollback
too), moves `target.database` / `target.schema` in place when the session moved and the target differs ("Now
in database b (USE)." / "Now in schema other (search_path)." in the messages), reloads completion and emits
`QueryTabEvent::Moved`, on which the workspace stores the tabs. The session is not rebuilt; other tabs and the
navigator do not change; a `None` (no database after MySQL's `DROP DATABASE`, no schema of the path exists)
leaves the target as it is. (An isolation change does not rebuild the session: `set_isolation` runs on it.)
MariaDB follows `USE` through the same MySQL driver path (`session.database()`,
pinned for both by `kerno-mysql/tests/introspect.rs::introspection_does_not_disturb_the_session`). Tests:
`kerno-postgres/tests/execute.rs::the_schema_follows_set_search_path` (connect, `SET`, `RESET`, `SET LOCAL` then
`ROLLBACK`, plain `SET` in a rolled-back block, `set_config` with a missing first schema, NULL);
`session::tests::statements_that_may_change_the_current_schema`; UI
`critique::use_in_a_tab_moves_its_picker_and_survives_a_reconnect` (MySQL),
`critique::use_in_a_mariadb_tab_moves_its_picker_and_survives_a_reconnect`,
`critique::set_search_path_in_a_tab_moves_its_picker_and_survives_a_reconnect` (with `SET LOCAL` then Roll
back): message, picker, status bar, the stored tab, the other tab unchanged, the tab's backend killed and the
server asked again (`database()` / `current_schema()` and a new backend id), back to the first place from the
picker. Limits: the target holds one schema, so `SET search_path TO a, b` comes back after a rebuild as `a,
public` (`Target` and the stored tab hold one schema; keeping the path would change the stored format and the
picker); `current_schema()` is the first schema of the path that exists (`missing, b` gives `b`); a function
called from a `SELECT` that sets the path (other than `set_config`) is not seen until the next matched
statement; `ALTER ROLE … SET search_path` changes nothing now and only reaches a rebuilt session whose target
has no schema; a session whose path has no existing schema keeps the picker on the old schema until a rebuild
puts it back there. Not K3: a script file bound silently, a deleted connection's tabs (K6). Plan errors:
`kerno-postgres/tests/session.rs` and `kerno-mysql/tests/session.rs` do not exist (the test is in
`execute.rs`; MySQL's `USE` was already covered in `introspect.rs`); one UI test per engine, not a loop over
MySQL and MariaDB: the stored tabs are the app's global storage, and the first engine's workspace, still alive,
stores its own tabs over the second's.

## K4 — An open transaction is visible on every tab, with its age (C15, C21)

**Now.** "transaction open" is in the status bar of the active tab only (`workspace.rs:3955-3961`); the tab
label's dot covers unsaved text and pending edits (`workspace.rs:347-358`); no age anywhere except per
statement inside the transaction log (`query/tx_log.rs:117`). Open a transaction in tab A, switch to B:
nothing says A holds locks.

**Wanted.**
- Tab strip: a query tab with `TxState::Open` shows a small warning-coloured badge after its title (a filled
  circle in `theme.warning`, distinct from the unsaved dot; `TxState::Failed` in `theme.danger`), with a
  tooltip "Transaction open for 4 min: Commit or Roll back (⌘⇧Enter …)" (use the real bindings of Commit and
  Rollback from `actions.rs`). The vertical tab list and the overflow menu (J10) show the same badge.
- Status bar: "transaction open · 4 min" (minutes; seconds under a minute), refreshed by a 15 s timer only
  while some tab has a transaction (no timer otherwise: idle CPU stays at zero).
- The tab records `tx_started: Option<Instant>` when its state goes `Idle → Open` and clears it on `Idle`
  (`query/tab.rs`, where `tx_state` is updated after a statement).
- Readable in both themes (WCAG AA against the tab background): check the contrast with the existing theme
  tests' helper.

**Tests.** `a_transaction_is_shown_on_its_tab_while_another_is_active` (C15): open a transaction in tab A,
switch to B; the strip element `("tab-tx", index_of_A)` exists, B's status bar says nothing, A's shows the age
after the simulated clock moves 2 min. `the_transaction_badge_goes_when_it_ends`.

**Acceptance.** From any tab, the user can see which tabs hold a transaction and for how long. **Captures:**
tab strip with one tab in a transaction, both themes, and the status bar.

Done: the badge and the status text follow the session's own state (`QueryTab::tx_state()`, read on each
frame), so no badge outlives its transaction whatever ended it; only the age depends on hooks.
`QueryTab::tx_started` (the executor's clock, so tests move it) is set by `note_transaction` when the tab sees
its session in a transaction and none was recorded, and cleared once it sees none: after the manual-commit
`BEGIN` (the age starts there, not after the first statement), after each statement (a typed `BEGIN` /
`START TRANSACTION`, `COMMIT`, `ROLLBACK`, MySQL's implicit commit), at the end of a run (a failed source
rolled back), after `finish_transaction` (Commit, Roll back, the environment's idle rule, K1's rollback at
quit), after applying a result's edits; `close_session` clears it (a lost connection, a disconnect, a moved
or rebuilt session, a closed tab). A failed transaction, or one back to a savepoint, keeps its start. The
badge: a 7 px dot in `theme.warning` (`theme.danger` once failed) after the title, outside the environment's
tint and before the close button, `("tab-tx", i)` in the strip, the rows and the side list (where the title
is cut and the dot stays), `("all-tabs-tx", i)` in the list of every tab; its tooltip and accessibility
description are `tabs::transaction_tip` ("Transaction open for 4 min: Commit (⌃4) or Roll back (⌃8).") with
the keymap's shortcuts, the user's file applied (`workspace::shortcut`; none invented when a command has
none). Status bar: `tabs::transaction_status` ("transaction open · 4 min", "transaction failed: roll back · 1
min"). `tabs::age_text` rounds down: "42 s", "4 min", "1 h 05 min". `Workspace::tx_ticker` is armed in

## K7 — Three classifier holes (C21)

**Now** (`kerno-core/src/sql/classify.rs`). Each returns `destructive = false`, so on a local or staging
connection with default settings it runs without the question; read-only and production still guard them
(they are writes).
1. MySQL versioned comments: `collect` (`classify.rs:263-283`) strips the version and always counts the body
   as SQL. `DELETE FROM t /*!90000 WHERE id = 1 */` on MySQL 8.4: the server skips the comment (90000 > its
   version 80400) and deletes every row; Kerno saw a `WHERE`.
2. PostgreSQL `PREPARE p AS DELETE FROM t` (and `… AS UPDATE t SET …` without `WHERE`): falls in `_ =>
   other(true)` (`classify.rs:418-420`); the inner statement is visible text.
3. `MERGE INTO t USING s ON true WHEN MATCHED THEN DELETE` (PostgreSQL 15+, `classify.rs:370`).

**Wanted.**
1. A `WHERE` found inside a versioned comment does not count as a `WHERE` (it may not run). Simplest correct
   rule, independent of the server version: collect the body for every other purpose, but mark its tokens so
   `has_where` ignores them. A statement whose only `WHERE` is in a versioned comment is destructive.
2. `PREPARE name [(types)] AS <statement>`: classify `<statement>` (as `EXPLAIN` does at `classify.rs:497`),
   keep `kind = Other`, `writes` and `destructive` from the inner statement. MySQL `PREPARE p FROM '<text>'`
   and a bare `EXECUTE`: unchanged (a text classifier cannot see them; they stay writes, so read-only and
   production guard them). Say so in a comment.
3. `MERGE … WHEN MATCHED [AND …] THEN DELETE`: destructive (it can delete without a condition the user
   reviews).
`REPLACE INTO` and `INSERT … ON CONFLICT/ON DUPLICATE KEY` stay non-destructive: they act on keyed rows.
`WHERE true` / `WHERE 1=1` stay non-destructive: an explicit `WHERE` is the user's decision (DBeaver does
the same); record it in `docs/DECISIONS.md`.
