Kerno 2026.11.4 backs up and restores MySQL and MariaDB databases on several connections at once, fills a
table with test data, and takes Windows further: an installer, updates installed from the app, the tools
and password files a Windows user already has.

If you run an earlier version on macOS or Linux, Kerno offers this update by itself: a dialog at launch, the
proposal in the status bar, or "Check for updates" in the About window. On Windows, 2026.11.3 does not check
for updates: install this one by hand once; from this version on Kerno offers the next ones there too.

## Install

| System | File |
|---|---|
| macOS, Apple Silicon | `Kerno-2026.11.4-macos-arm64.dmg` |
| Debian, Ubuntu (x86_64 / arm64) | `kerno_2026.11.4_amd64.deb` / `kerno_2026.11.4_arm64.deb` |
| Any Linux with glibc 2.31 or newer | `kerno-2026.11.4-linux-x86_64.tar.gz` / `kerno-2026.11.4-linux-aarch64.tar.gz` |
| AppImage | `Kerno-2026.11.4-x86_64.AppImage` / `Kerno-2026.11.4-aarch64.AppImage` |
| Windows, x86_64 (preview), installer | `Kerno-2026.11.4-windows-x86_64-setup.exe` |
| Windows, x86_64 (preview), no install | `kerno-2026.11.4-windows-x86_64.zip` |

`SHA256SUMS` lists the checksum of each file. The steps for each system are in the
[README](https://github.com/EvanPluchart/kerno#install).

On macOS the app is not notarized by Apple: the first time, open System Settings ▸ Privacy & Security and
click **Open Anyway**, or run `xattr -dr com.apple.quarantine /Applications/Kerno.app`.

On Windows the installer installs Kerno for your account only, without administrator rights, with a Start
menu entry and an uninstaller. Windows may warn about an unknown publisher (SmartScreen: "More info", then
"Run anyway"): the files are not signed. The zip still works without installing anything.

## New

- **Faster backup and restore for MySQL and MariaDB.** "Faster" in the backup and restore views writes one
  file per table into a folder and works on several connections at once, with a view of all tables taken
  at one moment for InnoDB; a large table is read in parts. The restore takes the folder as one backup,
  creates every table first, then loads the rows side by side. Measured on the test servers: a backup 1.9
  to 3 times faster, a restore 2 to 3.7 times. It works from MySQL 5.1 on; on a server before 5.5.3, or for
  tables that are not InnoDB, tick "Block writes during the backup" to have a large table read in parts.
- **Fill a table with test data.** "Fill with test data…" on a table (Generate Test Data… in the palette):
  a generator guessed for each column from its type and its name, foreign keys pointing at rows that exist,
  unique columns kept unique, a preview of the first rows, a seed that gives the same rows again. "Open
  script" writes the INSERT statements in a query tab and runs nothing; "Insert…" shows the first statement,
  asks, and inserts every row in one transaction. PostgreSQL, MySQL, MariaDB and SQLite.
- **Windows: an installer and updates from the app.** The installer needs no administrator rights. Kerno on
  Windows now checks for a new version as it does elsewhere and installs it: the download is checked against
  the release's `SHA256SUMS` before anything runs, Kerno quits, the installer replaces it and starts it
  again. If that fails, Kerno says so at its next start and points at the release page.
- **Windows: what you already have is found.** `~`, the `.ssh` folder of your profile and libpq's
  `%APPDATA%\postgresql\pgpass.conf` are read; installed PostgreSQL and MySQL/MariaDB clients are detected
  (Program Files, PATH) so that backup, restore and "Execute script" work; connection errors are told in
  plain words there too.
- **Windows: the tunnel through the system's OpenSSH.** A connection can go through Windows' own `ssh.exe`
  (System32's, or the one installed in Program Files; never one found on the PATH): the hosts of your
  `.ssh\config`, jump hosts and chains of them, the agent, every key type. Kerno answers the passphrase and
  the unknown-host question itself. On Windows no file of another computer is opened for a connection or a
  task (a key, a certificate, a database file, a backup): a path must be on a drive of this computer.
- **The macOS disk image opens on a designed window**: Kerno on the left, Applications on the right, an
  arrow between them.

## Better

- **Reconnect, the Read-only switch and saving an open connection no longer break the tree.** They left the
  tree reading through sessions that had just been closed: every schema not opened yet showed "connection
  closed: the session was closed", and neither Refresh nor Reconnect mended it. The tree now reads again on
  new sessions; a session ended by the server is replaced and the read done once more, without a question;
  when that fails the row says "The connection to “name” was lost. Reconnect it…" first, then the server's
  words. After a reconnect the tree comes back as it was: the same folders open, the same row selected.
- **Restoring a MySQL or MariaDB folder backup into a database that already holds its tables** says before
  it starts which tables will be dropped and replaced and which stay; after a failure or a cancel it reads
  the database and says which tables are loaded, empty or missing.
- **A MySQL or MariaDB folder backup restored into a database with another name writes nothing into the
  database it was taken from.** A trigger, a routine or an event typed with its database written out
  (`create trigger shop.t_bi … on shop.orders`) is kept as typed by the server and by mysqldump: restored
  into another database, it would be created in the first one. Kerno finds such statements before the run,
  says how many and which, leaves them out unless you tick "Load them as written", and names them at the
  end; an enabled event whose body names the first database is left out too. A plain dump whose header names
  another database than the target gets a warning.
- **Stopping a read on PostgreSQL** closes its session by cancelling the statement first: a stopped read no
  longer leaves a statement running on the server until it ends by itself.
- **The tree while a table is locked elsewhere** lists the schema's tables at once, without the size of the
  locked one, instead of waiting for the lock.
- **A table dropped by someone else while the tree reads** no longer shows "could not open relation with
  OID…": the read is done again.
- **Importing the same DBeaver project twice in a row** no longer risks a duplicate connection.
- **A run on several connections** shows its question as soon as a target asks for a confirmation.
- **An update that could not be installed** keeps its "Release page" item in the status bar and its notice
  until you close it.
- **A restore that could not be read to its end no longer says "Done".** When a file of a restore became
  unreadable half-way, or the client stopped reading its script on its own and ended without an error
  (`\q` in a psql script), the run could end well with the rest never run. It now fails and says which
  file it stopped in.
- **Importing connections when there is nothing to import** says so and turns its button off; a DBeaver
  project whose connections are all here still brings its new saved queries, and the button says what it
  will write.
- **mysqldump too new for an old server** (it writes no table and still ends well on MySQL 5.1) is said
  before the run, with the client to choose; a backup that read no column of a table now fails and removes
  its file; options that only make a tool print something and stop (`--version`, `--help`) are refused.
- **A backup in utf8mb4 from a client older than 5.5.3's** no longer turns four-byte characters into "?".
- Tooltips of the tree are never drawn over the dialog their row opens.

The full list, with the tests behind each item, is in
[docs/FEATURES.md](https://github.com/EvanPluchart/kerno/blob/main/docs/FEATURES.md).

## Known limits

- The macOS build is signed ad hoc, not notarized. The Windows files are not signed.
- Windows is still a preview. Its test suites now run on Windows against real PostgreSQL and MySQL servers
  at every change, and the installer and the update are tried there by scripts; nobody has used it by hand
  on a Windows desktop yet, and an update by a standard (non-administrator) account has not been tried on a
  real machine. A Kerno started "as administrator" does not install updates: it opens the release page. A
  Windows not installed in `C:\Windows` gets no update check and no tunnel through the system's OpenSSH (the
  built-in SSH client works). With Kerno in a folder whose name has a letter outside ASCII (other than the
  installer's own place in your profile), Windows' OpenSSH cannot start Kerno to ask a passphrase: Kerno
  says so, and the agent or the built-in client work. A tunnel for MySQL or for a backup tool listens on a
  local port for as long as it is open: other accounts of the computer can reach that port (they still need
  the database's login). Saved passwords are kept by Windows' Credential Manager; Kerno's own files rely on
  the access rights of your profile folder.
- The faster MySQL backup writes no replication position: use the plain backup (one file) to seed a
  replica. Without "Block writes", tables that are not InnoDB are not read at one moment with the others.
  Its restore drops and creates each table of the backup first: a restore stopped half-way leaves those
  tables empty until it is run again (Kerno says which).
- "Fill with test data" does not read CHECK constraints: a row that breaks one stops the insert, and
  nothing is kept.
- A psql or mysql script that stops itself (`\q`, `quit`) less than about 64 KiB before its end is not
  seen: the run ends well.
- Restoring a folder backup into another database: a `USE` line inside a table's own file, and SQL built
  inside a string by a routine, are not looked for; under a table named like its database a body's
  `name.column` can be taken for the database.
